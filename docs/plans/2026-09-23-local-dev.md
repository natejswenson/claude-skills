# local-dev implementation plan

## Request and acceptance

Source: the user's 2026-09-23 request for a faster, terminal-based alternative
to issueflow named `local-dev`.

- Accept a supplied feature description, an issue number/URL, or an interactive
  selection including **Enter your own item to work on**.
- Investigate the repository and ask only questions needed to settle scope,
  expected behavior, acceptance criteria, or consequential tradeoffs.
- Write a local implementation plan, independently red-team it, resolve findings,
  and commit the plan on a feature branch before implementation begins.
- Implement, test locally, review the local diff, commit, push and open a draft PR.
- Keep all intermediate work local: no issue creation, labels, comments, claims,
  remote checkpoints, PR review threads, polling or CI-wait loop.
- Support Claude Code and Codex from the same plugin. Preserve issueflow.

## Design

The agent owns development directly. Markdown files and Git history are the
checkpoints, with no orchestration daemon, stage-registration API or external
state store. A small dependency-free Node CLI provides read-only repository
inspection and explicit optional issue intake. It never edits Git or publishes.
Git commands remain visible, ordinary terminal operations run by the host.

The default local intake must work with Git and Node alone, including without a
remote or `gh`. The helper must not fetch, authenticate, run repository scripts,
or call GitHub during inspection. Issue browsing is a user-selected read; a
chosen issue is fetched once and saved with its source. Remote failures cannot
prevent independent local planning or implementation.

The workflow documents isolated worktrees for unrelated dirty work, branch/base
selection from repository instructions, plan and review filenames, a separate
plan commit, appropriately scoped testing, local review, and a single final
publication phase. Resume inspects those artifacts and Git rather than rerunning
stages or creating duplicate PRs. Ambiguous create/push outcomes require one
read-back before retry. Retry creation only after a successful read proves that
no matching PR exists; a failed read leaves publication pending, never permission
to create again. No merge, readiness change or release is implied.

## Implementation

1. Scaffold local-dev 0.1.0 with skillfactory; add both catalogs/manifests,
   workflow, release-component/check declarations, README and generated branding.
2. Author concise shared instructions plus a plan template and final-publication
   reference, including host-specific question and independent-review tools.
3. Implement `inspect`, `issues`, `issue`, and offline `report` helpers. Use
   argument arrays, bounded output, explicit flags and actionable nonzero errors.
4. Test against real temporary Git repos and a recording `gh` double: no remote
   calls on local intake, dirty/detached/empty repo behavior, base selection,
   filenames with whitespace, literal issue text and malformed inputs.
5. Exercise the workflow on this feature, freeze a real local inspection report
   for two-sided offline regression checks (real valid data passes, known-bad
   data fails), with refresh commands and an invariants declaration. Independently forward-test realistic entry,
   clarification, resume and publish-failure cases.
6. Generate help cards and Codex metadata; run skill and affected registry/brand
   checks, review, commit, then open a draft PR against main.

## Validation and boundaries

Run the new Node suite, score_skill, plugin/baseline lint, combined host checks,
skillfactory verification, press checks/tests and affected help/release tests.
Verify the workflow with ghfactory and its available local linters. Keep evidence
honest: a frozen intake report does not prove all model decisions or live PR
delivery. The independent walkthrough and this implementation supply separate
workflow evidence. Live repository settings, merge and release are out of scope;
the new required-check declaration takes effect only when an admin applies it.

## Risks and mitigations

- Excessive ceremony: keep only one independent plan review and focused local
  code review; revisit affected work only after a substantive change or finding.
- Unsafe Git staging: preserve unrelated changes, stage named paths and inspect
  the staged diff; never stash/reset/force-push automatically.
- Untrusted issue content: retain it as task data, not instructions or authority.
- Missing host delegation: disclose the limitation and perform an explicit
  adversarial self-review without claiming it was independent.
- Resume drift: compare the working branch and artifacts to the user's requested
  task before continuing; changed requirements update the plan first.

## Plan review

An independent reviewer found two omissions: ambiguous PR-create recovery must
not retry when read-back also fails, and the baseline must explicitly declare
its known-bad trap and refresh command. Both corrections are incorporated above.
The reviewer found the design viable and appropriately lean; no blockers remain.
