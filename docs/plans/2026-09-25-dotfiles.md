# Shared dotfiles management skill

## Request
Use local-dev and skillfactory to create a shared dotfiles management skill,
using the user's existing package-based checkout as the structural template.
The user confirmed that skillfactory is the builder intended by “skillbuilder”.

## Acceptance criteria
- Both Claude Code and Codex can discover and use the same dotfiles skill.
- Expected default location is `~/localrepo/dotfiles`, with explicit `--repo`
  and `--target` overrides. A legacy `~/.dotfiles` symlink may resolve to it;
  never create that alias or relocate a checkout implicitly. Missing or ambiguous
  repositories are reported rather than guessed.
- `packages.json` is the sole package allowlist. Package contents mirror target
  home paths. Tooling directories are not inferred to be packages.
- Read-only CLI inspection validates the manifest and reports correct links,
  missing links, conflicting files, wrong/broken links and parent blockers.
  Verification returns nonzero unless selected managed links are correct.
- Reject traversal, absolute/option-like package names, duplicate names,
  absent/zero-eligible-file packages, exact or ancestor destination collisions
  across all allowlisted packages (including unselected ones), symlinked package/source
  directories, source file symlinks and special files. Allow the checkout inside
  the target home (the expected layout); reject target at/inside the checkout
  and any managed destination or required parent that enters the checkout.
  Target ancestors may not redirect inspection through application symlinks.
- User flows cover inspection, editing managed sources, adding a configuration
  package, previewing and applying links, unlinking selected packages, and
  preserving/recovering individual conflicts. Live dependency installation,
  commits/pushes and moving whole directories require the relevant user scope.
- Preserve credentials, machine-owned agent config, global instructions/MCP
  state, local overrides, plugins/history and unrelated application files.
  Inspect known sensitive/runtime paths as excluded or blocked without reading
  their bodies; document that filename exclusions cannot certify secret absence.
- Tests exercise actual temporary filesystem layouts, two selected packages,
  spaces, arbitrary checkout locations and hostile manifests/symlinks. Include
  a checkout inside the target home, valid shared .config parents, ancestor
  collisions, excluded credentials and custom-ignore mismatch handling.
- Dogfood the documented edit/add-package/preview/link/unlink/recovery workflow
  against a temporary target, including idempotency and unrelated/local-override
  preservation. Use actual Stow when available and state any unavailable step.
- Run a real read-only inspection of the reference checkout. Freeze an offline
  topology replay baseline from reviewed metadata only: reconstruct temporary
  source/target files, rerun inspect/verify/report, enforce a nonzero file floor,
  and reject a deliberately unsafe classifier input. No personal
  configuration or account identifiers enter the public skill or test corpus.
- Wire both catalogs, version 0.1.0, changelog, CI/release component, PRESS target,
  baseline documentation and skillhelp index. Local conformance reaches rung 3.

## Decisions and scope
The reference repository uses GNU Stow with `--no-folding`, an explicit home
target, a package manifest, a bootstrap that separates dependency installation
from link maintenance, and individual-file conflict backups. Generalize that
structure, not its owner, package choices, shell helpers or configuration bodies.

The bundled Node helper is read-only. The agent performs authorized source edits
and uses an inspected repository installer (links-only) or explicit GNU Stow
commands after simulation. Never execute discovered scripts just because they
exist. Before mutation, reconcile the selected managed file set with repository
and global/local Stow ignore files, .stowrc and installer arguments. Run a reviewed
simulation with exactly the flags and policy used for application. Unknown policy
or a file-set mismatch blocks linking; protected files excluded by the inspector
must also be excluded by the actual installer. Ordinary management does not install
dependencies or call a full bootstrap. No custom installer or automatic migration
is introduced. No live dotfiles changes are part of building this skill.

Repository resolution: explicit path first; otherwise a qualifying current Git
root; otherwise `~/localrepo/dotfiles`; legacy alias only if unambiguous. Always
pass source and target explicitly for Stow; its default parent would be wrong.
The CLI itself accepts resolved explicit paths and never runs Stow or Git hooks.
