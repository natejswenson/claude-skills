# evals — what makes a baseline real instead of decorative

A baseline eval set is deterministic, offline, `$0`, and pinned against
artifacts from **a run that actually happened**. It runs inside the skill's own
test suite, so `ci / <name>` already gates it: no separate workflow, no new
required check, and — this is the point — **nothing in CI can spend money or
flake on a rate limit.**

LLM-judged harnesses stay manual and cost-capped. A gate that calls a model
turns every release into a coin flip.

## The four rules

### 1. Two-sided

Every baseline asserts good-input-passes **and** known-bad-input-fails. A
one-sided baseline silently rots the day someone weakens the checker — and
nothing about it looks different on the day it stops working.

This is why `skillfactory freeze` emits a *failing* test when no `--trap-command` is
given. A red test that says "this baseline is one-sided" is worth more than a
green one that asserts half of what it claims.

Prove it by mutation: break the checker on purpose and confirm the trap goes
red. skillfactory's own trap was verified this way — stubbing `validateSpec` to always
return ok left the golden green and turned only the trap red.

### 2. Anti-vacuity floors

Any corpus-driven check declares a minimum. A glob that quietly matches nothing
must go **red**, not green.

This is the most common way a baseline turns decorative, and it is nearly
undetectable: the suite passes, the check ran, it examined zero things. It has
bitten this repo more than once — a `r.errors ?? []` typo against a
`{ok, findings}` return once made 61 devlog entries report "all clean" while
checking nothing at all.

### 3. Floors for scores, byte-exactness only for generated artifacts

Use a floor (`score >= 0.8`) for anything judged, so normal variation does not
fail the build.

Use byte-exactness **only when the generated bytes are the contract** — a
rendered workflow, an emitted brand region, a scaffolded skill tree. In those,
one changed character is a change to shipped behaviour or appearance, so exact
comparison is the correct assertion rather than an over-strict one.

### 4. One-command refresh

Every frozen artifact declares an `update_command` in `skill-invariants.json`,
and the failing assertion prints it. A baseline nobody knows how to refresh
becomes a baseline people delete.

## Reproduce, don't just compare

Comparing a frozen file to itself asserts that nobody edited it. That is worth
something, but it is not an eval — behaviour can change completely while the
fixture sits untouched.

`skillfactory freeze` records the command that produced the run and generates a test
that **re-runs it into a temp directory and byte-compares**. That fails when the
skill changes, which is the thing you actually wanted to know.

The recorded command must be offline. Freeze refuses one that looks networked
(`curl`, `gh api`, an `npm install`, a URL) unless explicitly overridden.

## Pin against a real run, never a synthetic fixture

A synthetic fixture encodes what you *believed* the skill does. A real run
encodes what it *did*. The difference only shows up when you are wrong, which is
the only time an eval matters.

Where a real run is not available for every case, pin against real artifacts
that already exist: press pinned every brand value as it stood in eight files
across four repos *before* press generated any of them; skillfactory pins the nine
skills this repo already ships.

## Curate the corpus deliberately

Asserting over *everything* historical encodes "the checker must accept its own
history", which is a different and usually wrong requirement. devlog's corpus is
8 of 61 published entries on purpose — the other 53 predate rules that landed
later. Say why the subset is the subset, in the `rationale`.
